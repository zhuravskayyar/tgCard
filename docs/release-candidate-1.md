# Cardastika — Release Candidate 1

- **Дата перевірки:** 2026-10-24
- **Гілка:** `codex/cardastika-improvements`
- **Статус:** `NEEDS MANUAL QA`

Кандидат зібраний і перевірений локально. Публічний реліз не готовий: окреме staging-середовище, реальний Telegram Mini App і реальні Google/Telegram входи та прив’язки не перевірялися.

## Що увійшло до кандидата

- Гостьовий профіль і сесія створюються в одній транзакції. Якщо створення сесії падає, профіль відкочується.
- Сесія продовжується лише поки вона активна; прострочена або відкликана сесія відхиляється.
- Ліміт гостьових запитів зберігається в PostgreSQL: 5 спроб за годину і 20 за добу для однієї мережі. IPv6 групується за `/64`; зберігається HMAC IP, не сама адреса. Лічильник спільний між екземплярами сервера.
- Коли ліміт досягнуто, API повертає `429` і `Retry-After`, а стартовий екран пояснює користувачеві, що сталося.
- Прив’язка ідентичності серіалізована блокуванням профілю. Тести покривають конфлікт, повторну і конкурентну прив’язку, відхилення перенесення гостьового профілю та збереження рівня, XP, ресурсів, карт і колоди.
- 5 діамантів нараховуються транзакційно один раз на профіль і один раз на підтверджену пару провайдер + ідентифікатор. Повторне використання вже прив’язаного Telegram-профілю не створює нову нагороду.
- Виправлено напрямок відбиття шкоди дзеркальним артефактом і додано окремий регресійний тест.
- `vercel.json` збирає застосунок без міграцій і seed. Міграція 061 залишається окремою ручною дією.

## Перевірки

Усі наведені нижче автоматичні перевірки виконано з локальною PostgreSQL на `127.0.0.1:5432`, база `cardastika`.

- `npm run build` — успішно; shared, game-core, server і client зібрані.
- `npm test` — успішно: 71 перевірка game-core і 140 перевірок server, 211 разом.
- `npm run test:e2e` — успішно: 10 браузерних сценаріїв.
- Цільовий `accountAuthRoute.integration.test.ts` — успішно: 9 сценаріїв, включно з відновленням/відкликанням сесії, Google/Telegram прив’язками, конфліктами, одноразовою нагородою, `429` і спільним лімітом між двома екземплярами.
- Браузерна адаптивність перевірена на 320, 360 і 430 px. Перевірені клавіатурне керування діалогом, Escape, повернення фокуса, помилки дій, стани підтвердження та `prefers-reduced-motion` у наявних E2E сценаріях.
- Локальний frontend повернув HTTP 200 і сторінку Cardastika. `/api/health` через Vite-проксі повернув HTTP 200. Некоректний Telegram payload через локальний `/api` дійшов до auth handler і повернув 401.
- Окремий тимчасовий сервер на `127.0.0.1:3010` успішно стартував із тестовим bot token, під’єднався до локальної PostgreSQL (`SELECT 1`) і повернув здоров’я API. Сервер зупинено після перевірки; міграції та seed не запускалися.
- Перевірка чистого завантаження локального екрана в Chromium не виявила помилок консолі чи помилок JavaScript.
- `vercel.json` валідний JSON; `buildCommand` не містить `migrate` або `seed`.
- Локальна БД уже містила маркери міграцій 060 і 061. У цій перевірці міграції не запускалися.

- [PR #2](https://github.com/zhuravskayyar/tgCard/pull/2) — відкритий draft; Vercel статус зелений. Він перетинається з локальною роботою в екрані карти, коваля, магазину, арени й загальних стилях керування; локальний код уже має підтвердження поглинання через спільний `ConfirmationDialog`, вимкнене незавершене кування та підписані вкладки магазину. - Push, deploy і merge не виконувалися.

## Міграції, залежності та обмеження

- `061_guest_auth_abuse_controls.sql` створює таблицю лічильників і додає необов’язкові дані про ідентичність до таблиці нагород; міграція локально вже була застосована до початку цієї роботи. Production не змінювався.
- Нових npm-залежностей немає.
- Ліміт рахує спроби створення, а не лише успішно створені профілі. Люди за спільною NAT-мережею можуть ділити ліміт. Різні Google і Telegram акаунти однієї людини неможливо надійно зіставити, але повторно видати нагороду за ту саму підтверджену ідентичність не можна.
- Локальна конфігурація містить `CLIENT_ORIGIN` на домені `app.cardastika.org`, який задокументовано як production-домен. Його не відкривав і не використовував. Наявність тунелю або токена без окремого тестового бота не доводить, що зовнішній запуск ізольований.

## Неперевірено вручну

- Реальний Telegram Mini App із окремим тестовим ботом: валідний `initData`, вхід, перезавантаження, `TopHud` з реальними ім’ям, рівнем, сріблом і золотом.
- Реальний Google OAuth вхід з окремим staging OAuth client.
- Прив’язка Telegram і Google через справжні провайдери, повторні спроби та конфлікт уже зайнятої ідентичності у staging.
- Нагорода в реальному staging-профілі та підтвердження, що вона видана рівно один раз.
- Публічний HTTPS frontend та `/api` маршрут staging.
- Фізичні пристрої / Telegram WebView, анімації в реальному пристрої та ручна перевірка повного стартового шляху.

## Що потрібно для безпечного staging

1. Окрема disposable PostgreSQL, не production і не поточна локальна БД; окремі credentials і перевірений hostname.
2. Окремий тестовий Telegram bot token/username з Mini App URL на staging HTTPS.
3. Окремий Google OAuth client з staging origin.
4. Staging `CLIENT_ORIGIN` і API маршрут, підтверджені як ізольовані від production. Секрети передавати тільки через захищені environment settings.
5. Застосувати міграцію 061 тільки до цієї staging-БД, перевірити `/api/health`, реальні входи та `TopHud`, потім повторити ручні сценарії вище.

Поки цих налаштувань немає, зовнішня перевірка не виконувалася і production-конфігурація не використовувалася.

## Безпечний порядок релізу після QA

1. Переглянути цей звіт, локальний diff і обидва draft PR; вирішити, як оформити локально перенесене виправлення PR #1 та різницю текстів PR #2.
2. Завершити staging QA з окремими секретами та базою. Переконатися, що Vercel build тільки компілює код.
3. Після окремого дозволу підготувати перевірений backup production PostgreSQL через direct/unpooled Neon connection string.
4. Окремою контрольованою дією застосувати міграцію 061 до production-БД; перевірити marker, таблицю та індекси.
5. Після окремого дозволу виконати deploy і перевірити сайт, API, Telegram Mini App, реальний `TopHud`, Google/Telegram прив’язку й одноразову нагороду.

## План відкату

- Якщо проблема лише в коді — повернути попередній Vercel deployment, залишивши сумісну additive міграцію 061.
- Не видаляти таблицю ліміту чи колонки нагороди як терміновий відкат.
- Якщо треба відновлювати дані, зупинити записи, відновити перевірений pre-061 backup в окрему БД, перевірити її і лише після цього перемикати застосунок погодженим релізним процесом.

**Висновок:** локальний кандидат проходить збірку й автоматичні перевірки. Статус залишається `NEEDS MANUAL QA`, доки окреме staging-середовище та справжні Telegram/Google сценарії не перевірені.
